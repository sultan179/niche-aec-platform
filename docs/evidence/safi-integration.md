## 2026-09-16

## 2026-09-17

- **FACT (source: SAFI Import/Export menu, direct observation):** SAFI's Import/Export menu offers **Export SDNF, Export KISS, AutoCAD (DXF)**, and **Import IFC** / **Import STAAD**. **There is no Export IFC option.** SAFI is IFC-import-only — this reverses the earlier unconfirmed report.
- **FACT (source: `ifc_inspect.py` run on real file `data/ifc/Kingsway Apartments - 1 floor test.ifc`, 2026-09-17):**
  - Schema: IFC2X3, CoordinationView 2.0. Exported by Revit 26.4.10.51.
  - Units: feet internally (scale 0.3048 to metres); tool converts automatically.
  - 95 physical elements (24 `IfcBeam`, 23 `IfcColumn`, 48 `IfcMember`), all 95 with materials recognized.
  - **Only the 24 beams have a recognized section profile name — all columns and `IfcMember` elements have none.**
  - Zero analytical content (no `IfcStructuralAnalysisModel`, no members/nodes/supports, no `IfcRelAssignsToProduct` links) — this is a physical-geometry-only export.
  - `Tag` field is populated on physical elements (Revit's element ID) — a candidate for matching now that GlobalId round-trip can't go through IFC.

## Implication (RECOMMENDATION)

- SAFI integration will be file-based, but **IFC is import-only, one direction (Revit → SAFI)**. The return path (SAFI → Niche) has to use SDNF, KISS, DXF, or the Excel/Access reports — `ifc_inspect.py` cannot read any of those formats.
- The round-trip GlobalId test in `docs/evidence/ifc-test-protocol.md` (`compare R1.ifc S1.ifc`) **cannot run as written** — there is no `S1.ifc`. The protocol needs revision: either read GlobalId/Tag preservation from SDNF/KISS text output directly, or accept that matching must rely on **Tag** and geometry (position/grid), not GlobalId, for the SAFI side.
- Whether SDNF/KISS preserve Revit's `Tag` value is now the key open question for identity matching (HYPOTHESIS: worth checking before assuming Tag survives export any better than GlobalId would have).

## 2026-09-18 — Connectivity is a modeling-quality issue, not a platform limitation

- **FACT (source: drafter, 2026-09-18):** SAFI's connectivity tolerance is approximately 200mm (drafter's estimate, not an exact spec). Revit→IFC→SAFI import doesn't always auto-connect in their normal workflow. This matters — our earlier tests only tried 10mm and 50mm tolerances, far below what's actually used in practice.
- **FACT (source: drafter-provided "cleaned"/properly-connected file, `data/ifc/Cleaned/Kingsway Apartments - 1 floor test.ifc`, same building as the original test):** 79 physical elements (24 beam/23 column/32 `IfcMember` — fewer Members than the original 48). Same systemic gap as before: only beams have a section profile name; columns/Members don't.
- **FACT (source: SAFI import report, `Safi Report Cleaned Import.rtf`):** **0/172 floating members, 36/172 (21%) cantilever** — roughly 79% fully connected. This is essentially the inverse of the original file's 78–83% broken rate.
- **Conclusion (nuanced 2026-09-22, see below):** the messy file's near-total failure was a real modeling-quality issue specific to that file, not a SAFI/IFC platform limitation — a properly-connected Revit model imports dramatically better. But "dramatically better" is not "solved automatically": the Cleaned file still had 21% cantilever (one end free), and per the drafter, **some manual connection-fixing in SAFI is always part of the real workflow**, never fully automatic. This still substantially de-risks Problem A/B, but doesn't eliminate the need for the reconciliation tool this project is building.

## 2026-09-18 — Matcher validated on a second file; new gap found (segment splitting)

- **FACT (source: `match.py`/`report.py` re-run against the Cleaned file's SDNF export, `2026_05_13_Kingsway_V1 - TEST, 1 floor Connected.sdnf`):** the 90° coordinate transform and the SectionMapping dictionary (both built from the first file) **generalized cleanly** to this second, independently-connected export — 22/24 beams matched, zero new section mismatches.
- **FACT:** SAFI's connectivity generation **splits well-connected beams into multiple shorter sub-segments** at real connection points (the raw physical member count went from 79 to 172 after connectivity processing — same splitting behavior seen on the first file, now much more pronounced since more real connections exist). This broke 2 beams' 1:1 matching — the current matcher has no way to recognize "one Revit beam = several SAFI segments."
- **Implication (RECOMMENDATION):** this is exactly the "merge SAFI segments" normalization step `CLAUDE_INSTRUCTIONS.md` §8 already names as required, not a new architectural surprise. Next build priority: 1:N segment-merging support in the matcher.

## 2026-09-22 — Root cause of segment splitting found: a real small gap in Revit's own model, bridged by SAFI's tolerance

- **FACT (source: SAFI Member Attributes dialog, direct observation, live inspection of the beam run at the two unexplained split points from 2026-09-18):** the element bridging one gap is a **"Rigid Member"** — `Member Type: Offset/Dummy`, `Section: Rigid Member [Rigid]`, length **93.4mm**, connecting `Joint 22` to `Joint 92` (in that import session). Not detectable from the SDNF export.
- **FACT (source: Sultan, direct comparison, 3 screenshots):** re-importing the same IFC with connectivity tolerance set to **0mm** shows the real, unprocessed geometry — two distinct points with a genuinely visible gap between them, not one merged point. So the gap is real, not an import-rounding artifact.
- **FACT (source: cross-referencing SAFI's 0mm-tolerance Joint 22 coordinates against the Revit IFC data via `ifc_inspect.py`'s extracted physical elements):** Joint 22's elevation (**3788.41mm**) matches, to 4 decimal places, the endpoint elevation of a nearby `IfcMember` (profile `W16X26`, likely a diagonal brace) in the Revit export (**z = 3.7884m = 3788.4mm**). **This is an exact match, not inference.**
- **Corrected conclusion (my first hypothesis, "IFC coordinate rounding," was wrong and has been replaced by this verified one):** the "unexplained" splits are **a real, small gap that already exists in the Revit model** — a secondary/diagonal member (the `W16X26` `IfcMember`) frames in near the main beam but its endpoint isn't snapped exactly onto the beam's line, leaving a real ~200mm-scale gap. SAFI's connectivity tolerance (~200mm, the drafter's estimate) decides whether to bridge that real gap with an auto-inserted Rigid Member, or leave it visibly disconnected at 0mm tolerance. This is a genuine drafter-modeling characteristic, not an IFC/SAFI pipeline artifact.
- **Why our SDNF-based proximity search (`find_junctions.py`) found nothing at first:** SDNF is a **steel detailing** format — it excludes non-physical `Offset/Dummy` Rigid Members, so the bridging element is invisible to any tool reading SDNF alone. The real explanation only surfaced by cross-referencing SAFI's live joint coordinates against the Revit-side data directly.
- **Implication (RECOMMENDATION) for the matcher:** since the underlying cause is a real small Revit-modeled gap (not an import artifact), the practical fix for 1:N/chain matching is still the same — widen the *outer* endpoint tolerance when matching a Revit beam (or run) against its SAFI segment chain, bounded by SAFI's ~200mm tolerance — but now for the right reason: real secondary members can frame in without landing exactly on the primary line, and SAFI's own tolerance setting determines whether that shows up as a rigid-linked split or a disconnected floating member.

## 2026-09-22 — Workflow clarification: IFC import is never auto-connected; manual fixing is always part of the real process

- **FACT (source: drafter, via Sultan, 2026-09-22):** the real workflow is: draft in Revit → export IFC → import into SAFI → **connections always come in broken to some degree** → the drafter either manually fixes them in SAFI, or rebuilds the analytical model from scratch in SAFI. This is stated as always true, not an edge case.
- **FACT:** the IFC file is always the raw, as-exported-from-Revit output — SAFI never touches or modifies it (consistent with D-013: SAFI has no IFC export). Any "native SAFI project file" (`.gse`-type) that shows as properly connected is **the drafter's manually-corrected end result**, not evidence that a well-modeled Revit file imports cleanly on its own.
- **Correction to the 2026-09-18 conclusion:** the Cleaned file's much-better import result (0% floating, 21% cantilever vs. the messy file's 78-83% broken) is real and still meaningful — better Revit modeling clearly reduces the amount of manual correction needed. But it does not mean connectivity is "solved" by clean modeling alone; the drafter's stated reality is that manual fixing in SAFI is **always** required, at minimum for remaining cases like cantilevers. This reinforces plan.md's Problem A/B (manual reconciliation is the core problem) rather than undermining it.

## 2026-09-22 — Section AND material catalog sync direction: SAFI is source of truth, drafter syncs Revit to match

- **FACT (source: drafter, via Sultan, 2026-09-22):** Revit and SAFI each pull from their own separate standard catalog (Revit: imperial W-shape names; SAFI: metric names). Sizing/material decisions get finalized during structural analysis in SAFI, and the drafter then **manually updates Revit to match whatever SAFI ended up using** — for both section sizes and materials. Confirmed explicitly: "same for materials as well."
- **Implication (RECOMMENDATION):** the SectionMapping dictionary isn't solving a hypothetical problem — it's formalizing a translation the drafter is **already doing by hand**, every project, in both directions (SAFI import auto-recognition, and the post-analysis manual sync back to Revit). This also reframes the reconciliation report's purpose precisely: the drafter's process *intends* Revit and SAFI to always match; the report is the check that the manual sync actually happened correctly for every element, not a replacement for their judgment.
- This directly answers the earlier open question ("how does the drafter know materials match") — they don't have an automated check today; it's a manual, per-element sync after analysis, which is exactly the kind of step a human can miss on a busy project. A MaterialMapping dictionary (same pattern as SectionMapping) is a natural next extension, not yet built.

## 2026-09-17 (continued) — SAFI import: identity not retained

- **FACT (source: SAFI Member Attributes dialog, direct observation, member Phys #90):** after IFC import, the member's **Name** field is `#5184 : W Shapes:W1` — truncated (the original Revit type name, e.g. "W18X40", is cut off), and the leading number (`5184`) does not match any Revit Tag/GlobalId seen in the source IFC (Tags were in the 1,280,000s). This looks like SAFI's own internal numbering, not a preserved Revit identifier.
- **Implication (RECOMMENDATION):** SAFI does not retain a usable Revit identity (Tag or GlobalId) anywhere after import — not because SAFI can't export IFC, but because it appears to discard/replace the source ID on import itself. **ID-based matching (GlobalId or Tag) is not viable for the SAFI side.** Matching for the comparison tool must rely on **geometry/position** (coordinates, grid reference), which does survive — this doesn't create a new problem, it confirms the plan's existing D-002 choice (geometry-based matching first, ML later) was correct.
- **FACT (source: SAFI Import report, `data/ifc/SAFI report.rtf`, two import runs on the same file):** at 10mm offset tolerance, 57/95 members floating + 22/95 cantilever (83% with a connectivity issue). At a larger tolerance, 53/107 floating + 30/107 cantilever (78%) — member count grew from 95→107 (tolerance increase caused unwanted member splitting), while the problem rate barely improved. This points to a real geometry/connection gap in the source model, not an import-tolerance issue — needs the drafter to confirm by inspecting specific floating members.
- **FACT:** on import, 2 of 4 materials were unrecognized by SAFI (`01 Steel 6x6`, `01 Steel Main Framing` — custom Revit material names not in SAFI's library).

## 2026-09-23 — Three-way diff mechanism built: baseline save/load + change classification

- **FACT (source: `tools/ifc_inspect/baseline.py`, `three_way_diff.py`, built this session):** the three-way diff from plan.md §6/§11 is now implemented as: `save_baseline()` writes a report DataFrame to `data/ifc/baseline.json`; `diff_against_baseline()` loads it back, joins against a freshly-built current report on `revit_id`, and classifies each element as `unchanged`, `new`, `missing`, `changed in Revit only`, `changed in SAFI only`, or `conflict - changed in both`.
- **DECISION:** the diff is keyed by **Revit GlobalId**, not SAFI's `piece_id`. Revit's GlobalId is proven stable across re-exports (see 2026-09-17 below). SAFI's `piece_id` has only been proven unique *within one export* — whether the same physical member gets the same `piece_id` across two separate exports of the same model has never been tested. Keying on GlobalId sidesteps that unknown entirely; SAFI-only elements (no Revit match) currently have no cross-time identity and are excluded from the three-way comparison — a real, open gap, not yet needed since no case has required tracking them across time.
- **FACT (bug found and fixed):** the first version compared fields with plain `!=`, which produced 55/78 elements falsely flagged as changed on a same-data-against-itself test (expected: 100% unchanged). Root cause confirmed by inspecting raw values directly (not assumed): both baseline and current genuinely had `nan` (a `float`) for the same missing field (e.g. `revit_section` on columns, per the known systemic profile-loss issue) — and in Python/IEEE-754, `float('nan') != float('nan')` is always `True`, even comparing the value to itself. Fixed by normalizing any non-string value to `None` before comparing (`_norm()` in `three_way_diff.py`), same pattern already used in `build_section_mapping.py`.
- **FACT (verified after the fix):** running the identical Cleaned-file data against a baseline saved from that same data now returns **78/78 unchanged**, as expected.
- **Known limitation, not yet fixed:** `matched (chain)` rows use a semicolon-joined string (e.g. `"id1; id2"`) as their `revit_id` key. If the same beams get grouped into a different chain combination on a later run, this shows as one row "missing" and another "new" instead of "unchanged" — noisy but not wrong. Only one real chain case exists so far, so not yet prioritized.
- **FACT (verified via simulation, source: scratch test script run against the real `baseline.json`):** took the saved baseline, mutated 4 real matched elements in a copy of it (Revit section only, SAFI section only, both, and one element removed entirely), plus added one fake new element. All 5 classified correctly (`changed in Revit only`, `changed in SAFI only`, `conflict - changed in both`, `missing`, `new`), and all 73 untouched elements stayed `unchanged` — zero false positives.
- **FACT (verified end-to-end with a genuine real-world change, 2026-09-23):** opened the real Revit project behind `Kingsway Apartments - 1 floor test.ifc`, changed one Girder's section from `W18X40` to `W21X44` (Structural Framing, TOS 2ND FLOOR), re-exported IFC (`Kingsway Apartments - 1 floor test Changed.ifc` — same 24 beam/23 column/32 member/79 physical-element counts as the original export, confirming nothing else moved), ran it through the full pipeline (`ifc_inspect.py` → `report.py` → `diff_against_baseline()`) against the existing SAFI SDNF (untouched) and the saved baseline. Result: **77/78 unchanged, exactly 1 flagged `changed in Revit only`** — the edited girder, correctly showing `W18X40 → W21X44`. This closes the "simulation only" gap — the diff mechanism is now proven on a real Revit edit, not just mutated data.
- **FACT (verified end-to-end with a genuine SAFI-side change, 2026-09-23):** opened the real SAFI project behind the Connected SDNF, changed one member's (M55, Phys #55) section from `W460x60` to `W530x66` via the Member Attributes dialog, exported a new SDNF, ran the pipeline against the original (untouched) Revit report and the saved baseline. Result: **77/78 unchanged, exactly 1 flagged `changed in SAFI only`**, correctly showing `W460x60 → W530x66` on the SAFI side and `W18X40` unchanged on the Revit side.
- **FACT (verified end-to-end with a genuine conflict — both sides changed independently, 2026-09-23):** M55 reverted back to `W460x60` first. Looked up the SAFI counterpart of the already-changed Revit girder (`revit_id 29Xxu_V9b6oAbRiIM7xt6P`) in the baseline data — it's **Phys #57** (`#4166 : W Shapes:W1`), not M55. Changed Phys #57's section from `W460x60` to `W530x66` in SAFI, exported a new SDNF, paired it with the already-changed Revit report (`W18X40 → W21X44`) for that same element, and diffed against the baseline. Result: **77/78 unchanged, exactly 1 flagged `conflict - changed in both`**, correctly showing both sides diverged from baseline (`revit_section: W18X40→W21X44`, `safi_section: W460x60→W530x66`).
- **Three of five diff paths now proven on genuine real edits**, all on the correct matched element pair each time: `changed in Revit only`, `changed in SAFI only`, `conflict - changed in both`. Remaining: `new` and `missing`, both simulation-only — real tests would require actually adding or deleting an element in one of the live models, a more invasive/riskier edit than a section swap.

## 2026-09-17 (continued) — Geometry-based matcher: first real result

- **FACT (source: `tools/ifc_inspect/parse_sdnf.py` + `match.py`, real data — Revit physical elements vs. `Safi Export.sdnf`):** a real coordinate transform exists between Revit and SAFI: **`SAFI_x = Revit_y, SAFI_y = -Revit_x`** (a clean 90° rotation, no offset, no scaling), derived from 5 exactly-matching column positions. Z (elevation) matches directly, no transform needed.
- **FACT:** applying that transform, a mutual-best-match geometry matcher (hard filter by category, nearest endpoint pair) matched **47/47 SAFI elements to Revit elements at sub-millimeter precision** (0.0–1.2mm offsets — effectively exact). All beams and columns in the SAFI export matched correctly.
- **48 Revit elements (all `IfcMember`) went unmatched** — this is exactly the count of `IfcMember` elements in the source IFC. Cause unconfirmed: Sultan suspects this may be an export setting/mistake on the SAFI side (not everything selected for export), not necessarily a SAFI limitation. **Not investigated further — deprioritized per Sultan.**
- **Implication (RECOMMENDATION):** this is strong positive evidence for the geometry-based matching approach in §8/§9 of `CLAUDE_INSTRUCTIONS.md` — once the coordinate transform is known, matching is effectively exact, not just "good enough." This meaningfully de-risks Phase 1 (MVP-1).
